# B3.1 — Integración real Appwrite

## Objetivo

Validar contra la instancia real de Appwrite que la estrategia transaccional usada por el backoffice mantiene la consistencia de una anulación y revierte todas las escrituras cuando la transacción se hace rollback.

## Workflow

`.github/workflows/core3-appwrite-integration.yml`

Se ejecuta en `Core3` ante cambios relevantes o manualmente mediante `workflow_dispatch`.

## Secretos requeridos

Configurar como **Repository secrets** en GitHub Actions:

- `APPWRITE_ENDPOINT`
- `APPWRITE_PROJECT_ID`
- `APPWRITE_DATABASE_ID`
- `APPWRITE_API_KEY`

Nunca versionar estos valores.

## Escenario A — commit

El test crea datos aislados con IDs prefijados `core3-b31-*`, ejecuta una transacción que:

1. reduce `product.existence`;
2. crea el movement `ajuste` con `reason = purchase_entry_reversal` y `entry_id`;
3. cambia `purchase_entry.status` a `CANCELLED`;
4. hace `commit`.

Después comprueba que:

- `existence` se redujo correctamente;
- `reserved` no cambió;
- `last_unit_cost` no cambió;
- la entrada quedó `CANCELLED`;
- el movement quedó persistido y trazable por `entry_id`.

## Escenario B — rollback

El test crea una entrada y producto aislados, prepara modificaciones dentro de una transacción y ejecuta `rollback` antes de persistir.

Comprueba que:

- `existence` conserva su valor original;
- `reserved` conserva su valor original;
- `last_unit_cost` conserva su valor original;
- `purchase_entry.status` sigue `ACTIVE`;
- no existe movement de reversión.

## Criterio de aceptación

B3.1 no se marca como integración verificada hasta que ambos escenarios pasen contra Appwrite real en GitHub Actions.
