# Core 3 B3.0 — Auditoría del contrato real de stock

**Fecha:** 2026-08-29  
**Rama:** `Core3`  
**Estado:** completada.

## 1. Alcance

B3.0 audita `existence`, `reserved`, `available`, `stock_movements`, `last_unit_cost` y las operaciones que los modifican, y determina si el Client SDK TypeScript de Appwrite puede proporcionar la atomicidad necesaria sin una Function serverless adicional.

## 2. Contrato confirmado

### Product

- `existence`: unidades físicas. Las entradas incrementan `existence`; las ventas VERIFIED la decrementan.
- `reserved`: unidades comprometidas por soft-hold. Las entradas no lo modifican.
- `available = max(0, existence - reserved)`.
- Invariante de dominio: `existence >= reserved`.
- `lastUnitCost`: último costo unitario de compra en USD; solo se actualiza por líneas `concept = purchase` con costo > 0.

## 3. Capacidad real de Appwrite Client SDK

El backoffice tiene `appwrite ^22.4.0` en `package.json`/lockfile. El tag oficial `22.4.0` del Web SDK contiene la API de `Databases` para operaciones numéricas con `transactionId`; la documentación actual confirma el mismo contrato de transacciones: `createTransaction`, operaciones staged con `transactionId` y `updateTransaction` para commit/rollback. citeturn101file0turn2search4

La estrategia adoptada es por tanto:

`AppwriteTransactionRunner → Databases.createTransaction() → transactionId → writes → updateTransaction(commit/rollback)`

No se requiere una Function serverless para B3.

Appwrite además detecta conflictos concurrentes al commit cuando una fila afectada cambió fuera de la transacción. El límite Free documentado es 100 operaciones por transacción, por lo que el caso de uso limita explícitamente el tamaño de las operaciones. citeturn2search2

## 4. Entrada actual y migración Core 3

`RegisterPurchaseEntryCaseUse` ahora acepta un `TransactionRunner`. Cuando el runner de producción está inyectado, cabecera, líneas, productos y movements pasan el mismo `transactionId`. Un fallo al crear un movement ya no se acepta como `soft-fail`: aborta la operación y el runner solicita rollback.

La infraestructura concreta es `AppwriteTransactionRunner`, ubicada en `src/core/infrastructure/data/appwrite/`, y se inyecta desde `purchase.container.ts`.

## 5. Stock movements

Tipos existentes confirmados:

- `entrada`
- `salida_venta`
- `ajuste`
- `devolucion`

El modelo usa `quantity > 0`; la semántica del movimiento viene dada por `type` y `reason`.

B3.1 reutiliza `type = ajuste` con:

`reason = purchase_entry_reversal`

y conserva `entry_id`. No se introduce un nuevo enum ni una segunda estructura de movimientos.

## 6. Contrato de anulación B3.1

Para cada SKU afectado:

`newExistence = existence - totalQuantityOfEntryForSku`

y debe cumplirse:

`newExistence >= reserved`

Todas las líneas se validan antes de mutar stock. Las líneas repetidas del mismo producto se agregan primero para evitar decrementos parciales o cálculos basados en el mismo snapshot.

La reversión:

- no modifica `reserved`;
- no modifica `lastUnitCost`;
- crea un movement compensatorio;
- marca la entrada `CANCELLED`;
- no elimina entrada, líneas ni movements originales.

## 7. Idempotencia y concurrencia

La transición válida es:

`ACTIVE → CANCELLED`

Una entrada ya cancelada se rechaza antes de generar movements. Las operaciones se ejecutan con `transactionId`, por lo que Appwrite puede detectar conflictos concurrentes al commit. citeturn2search2

## 8. `lastUnitCost`

No existe historial suficiente para reconstruir automáticamente un costo anterior. B3.1 no pone `lastUnitCost` a cero ni intenta inferirlo. El operador continúa consumiendo el valor existente para COGS.

## 9. Schema pendiente

El dominio y DTO ya contemplan `status?: ACTIVE | CANCELLED`, pero el atributo Appwrite `purchase_entry.status` debe ser provisionado administrativamente antes de habilitar la operación en producción. El Client SDK no puede crear/modificar atributos de schema dentro de una transacción.

## 10. Resultado B3.0

**Completado y resuelto:**

1. Atomicidad: **Appwrite Client SDK**, sin Function serverless.
2. Reversión: **`ajuste` + `purchase_entry_reversal` + `entry_id`**.
3. `lastUnitCost`: **no se revierte en B3.1**.
4. `reserved`: **no se modifica**.
5. Registro de entradas y anulación usan la misma frontera transaccional.
6. La única dependencia administrativa pendiente es `purchase_entry.status`.

B3.1 puede continuar sobre esta infraestructura.
